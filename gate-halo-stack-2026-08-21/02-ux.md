# GauntletGate Full Lane — UI/UX Designer Deep-Dive

**Target:** halo-stack @ master `b1cb22a` · **Role:** UI/UX Designer · **Scope:** `mission-control/mission-control.mjs` (STALLED state, stop control, alarm strip), the two PowerShell launchers' failure UX, console accessibility, and copy in README.md / site/index.html / the console.

Built on the Walkthrough lane's report (`gate-halo-stack-2026-08-21/00-walkthrough.md`) rather than re-walking first-run. All findings below are from direct code reading (`mission-control.mjs`, `Start-DSH.ps1`, `Start-MissionControl.ps1`, `README.md`, `CHANGELOG.md`, `site/index.html`) plus one pixel-level screenshot inspection, not from comments describing intent.

## Role + severity counts

Blocker 0 / Critical 0 / Major 6 / Minor 3 / Nit 3

## Findings

### 1 — STALLED row's status dot has no matching CSS rule and renders invisible — **Major**

**Category:** visual-state / color-signaling

**Evidence:** `mission-control.mjs:1767` renders a stalled session's dot as `<span class="dot bad"></span>`. The stylesheet defines `.dot{...}` (line 961) and then colors four state modifiers at line 962: `.up{background:var(--green)}.down{background:var(--red)}.busy{background:var(--amber)}.wait{background:#5f8fd9}`. There is no `.bad` rule anywhere that sets a background color — a full-file grep for `\.bad\b` finds only `.vstat b.bad`, `.pchip.bad`, and `.alarm.bad`, none of which match `<span class="dot bad">`. Every other row state (up/down/busy/wait, used identically at lines 1391, 1677, 1768, 1842, 1848, 1852) gets a colored dot; STALLED — the one state this exact review is scoped to — gets a 9×9px circle with no fill, blending into the panel background.

**Observed vs expected:** Expected: the highest-severity row state has the most visually distinct dot. Observed: it has none.

**Why it matters:** The row's word "STALLED" plus amber duration text (`v-warn`) still carries the meaning, so this isn't a comprehension failure — but it breaks the "scan the dot column" mental model the rest of the table trains, at the exact moment scanning matters most (a table of 30+ sessions, the stalled one is supposed to jump out).

**Impact scope:** Every render of the Sessions tab whenever any session is stalled — the primary display surface for the feature under review.

**Fix path:** Add `.dot.bad{background:var(--red)}` (or reuse `.down`) next to the other dot-color rules.

### 2 — The hero state line never shows STALLED, and directly contradicts the alarm strip a few pixels above it — **Major**

**Category:** information-hierarchy / consistency

**Evidence:** `mission-control.mjs:404, 438-441` — a stalled session is `stalled:true` but `running:false` by design (`running: !!s.running && !(... > STALL_MS)`). The Overview tab's hero line (lines 1404-1412, itself commented "One explicit statement of what the machine is doing, so a screen full of zeros reads as idle rather than broken") only ever renders `COCKPIT DOWN`, `WORKING`, or `IDLE`:
```
var running=s.sessions.filter(function(x){return x.running});
...
if(!s.services.cockpit){ cls='down'; word='COCKPIT DOWN'; }
else if(genModels.length||running.length||s.jobs.active.length){ cls='busy'; word='WORKING'; }
```
Because a stalled session is excluded from `running`, none of these branches fire for it. Meanwhile the alarm strip immediately above (computed at lines 1274-1279, rendered via `renderStrip`) correctly turns HARNESS red with "N session(s) claim to be running but have not advanced... stop them or investigate."

**Observed vs expected:** Expected: the console's single largest, most prominent status word agrees with its own alarm strip. Observed: on the default landing tab, a user can see "HARNESS 🔴 — stop them or investigate" in the strip and "IDLE — last inference 2h ago" in the hero line, on the same screen, at the same instant.

**Why it matters:** This is precisely the class of defect the STALLED feature exists to prevent — a piece of UI asserting calm while something is actually wrong — just relocated from the row to the hero line instead of eliminated. A user who trusts the big text over the small strip (a reasonable default for "what's the one-line status") gets the wrong answer.

**Impact scope:** The Overview tab's primary status line, every time a session is stalled — Overview is the default tab (`showTab((location.hash||'#overview').slice(1)||'overview')`, line 1207) and the first thing a returning user sees.

**Fix path:** Add a `cls='stalled'; word='STALLED'` branch ahead of the WORKING check when `s.sessions.some(x=>x.stalled)`, styled distinctly from `busy`.

### 3 — Stop-session feedback is spatially disconnected from the row, and the row doesn't update (or disable its button) during the gap — **Major**

**Category:** feedback-timing / interaction-state

**Evidence:** `stopSession()` (lines 1211-1224) puts its only status text in `#actionMsg`, which sits directly under the master strip at the very top of the page (`mission-control.mjs:1035-1036`), while the row and its "stop" button live in `#tab-sessions` (line 1087), potentially dozens of rows down a sorted, filtered table. The function never disables the clicked button, never touches the row's own markup, and defers the table refresh: `setTimeout(function(){ msg.textContent=''; loadSessions(); },2500)` — 2.5s after the fetch *resolves*, not from click time. There is no per-row pending/spinner state anywhere in the file (`grep -n "disabled"` finds a `button:disabled{opacity:.5}` CSS rule that is never applied by any JS in the file — confirmed system-wide, not just for stop).

**Observed vs expected:** Expected (asked directly in scope): does the UI lie during the gap? Observed: yes, for a bounded window. Click → confirm() → fetch (variable latency) → the row still shows "STALLED 4h41m" with a fully clickable "stop" button, unchanged → text appears far away at the top of the page, easy to miss if the table is scrolled → the row itself stays stale until the next refresh. In practice this is capped by the ambient 5s poll (`setInterval(...); if(currentTab==='sessions') loadSessions();`, lines 2502-2507) racing the function's own 2.5s timer, so the lie self-corrects within roughly a click-to-network-latency-plus-≤5s window — but for that whole window the row is a false claim sitting directly beside the button the user just pressed, and nothing stops a second click landing on the same in-flight session.

**Why it matters:** The console's own design philosophy (per the STALL_MS/stalled-session comments) is "a truth console does not relay an upstream claim it can check." The row's own post-stop behavior violates that same principle for several seconds, with the confirmation the user needs placed somewhere they're not looking.

**Impact scope:** Every use of the stop control — the one safety-critical action this review is scoped to.

**Fix path:** On click, disable that row's button and swap its state to "stopping…" inline; on the fetch resolving, either update that specific row in place from the response or call `loadSessions()` immediately instead of after a fixed 2.5s pause. Move (or duplicate) the outcome text next to the row, not only to the global message line.

### 4 — Several interactive elements, including one that gates a link, are unreachable by keyboard — **Major**

**Category:** accessibility / keyboard

**Evidence:** A full-file search for `aria-|role=|tabindex` returns **zero** matches in 2720 lines. Five distinct custom-interactive patterns are built on non-focusable tags with only an `onclick`, no `tabindex`, `role`, or key handler:
- `mission-control.mjs:1759` — `<tr class="clickable" onclick="toggleSessionDetail(i)">`, the only way to reveal a session's detail row (`sdetail-i`, lines 1784-1789), which itself contains the only `<a href="http://127.0.0.1:3080">Open in cockpit</a>` link for that session.
- `mission-control.mjs:1345` — the alarm-strip light items (`<span class="light-item" onclick="location.hash=...">`) — the alarm strip explicitly in scope for this review.
- `mission-control.mjs:1826, 1832` — plugin summary filter chips.
- `mission-control.mjs:1919` — memory-graph entity rows.

By contrast, the **stop button itself is a real `<button>`** (line 1781) and every tab button is a real `<button>` (lines 1038-1043) — both are natively focusable and keyboard-operable, and I confirmed no `outline:none` anywhere in the file suppressing the browser's default focus ring. So the specific "new control" named in scope passes; the surrounding console does not.

**Observed vs expected:** Expected: every piece of information a mouse user can reach, a keyboard user can too. Observed: session-level detail (sessionId, exact token counts, goal text, and the only "Open in cockpit" deep link for that row) is completely unreachable without a mouse, since a keyboard user cannot Tab to the `<tr>` to expand it in the first place.

**Impact scope:** Keyboard-only and screen-reader users lose access to session detail drill-down and its embedded link, plus three lesser navigation shortcuts (alarm-strip jump, plugin filter, memory-graph drill-down). Primary flows (tab switching, load/unload, stop) are unaffected.

**Fix path:** Either make the toggle a real `<button>` wrapping the row content, or add `role="button" tabindex="0"` plus a `keydown` handler for Enter/Space to each pattern above.

### 5 — Both launchers are silent end-to-end for up to ~240s+, with zero progress indication, and a second click during that window is swallowed with no user-visible feedback — **Major**

**Category:** first-run-feedback / newcomer-UX

**Evidence:** Neither `Start-DSH.ps1` nor `Start-MissionControl.ps1` contains a single `Write-Host`/`Write-Output` (grep confirms zero). The documented shortcut target is `powershell.exe -NoProfile -WindowStyle Hidden ...` (README.md:117,119), so there is never a console window, in success or failure. `Start-DSH.ps1`'s own comment names the problem: "a second double-click during the up-to-240s hidden startup window" (line 24) — backed by the code's own budgets: up to 60s waiting for the LM Studio API (line 99), then up to two brain-load attempts of unbounded duration each (lines 114-121, and per the Walkthrough's W1, a verification bug can force a redundant full 21GB reload here), then up to 180s waiting for the cockpit to serve (line 184). During all of this, nothing is visible anywhere on the user's screen. The single-instance mutex correctly prevents a second click from racing the first (item 9 in the header comment) — but the guard is silent: `"another launcher is already starting the stack - exiting quietly" | Add-Content $log` (line 72), no dialog, no toast, nothing on screen.

**Observed vs expected:** Expected: a newcomer double-clicking a desktop icon gets some visible acknowledgment that something is happening. Observed: nothing happens on screen for anywhere up to several minutes, and a frustrated re-click (the natural response to apparent nothing happening) is deliberately, silently absorbed.

**Why it matters:** For a first-run newcomer, "silently doing nothing for 4 minutes" and "silently broken" are visually identical states. This is not a rare edge case — it is every single launch, and it compounds directly with the Walkthrough's W1 (the verification bug that can force a redundant 21GB reload, extending the silent window further on exactly the first-run path this launcher exists to smooth). Related to Walkthrough W3 (the LM Studio start-error case waits the full 60s unnecessarily) but distinct: W3 is about wasted time, this is about the complete absence of any progress signal regardless of how long the wait legitimately is.

**Impact scope:** Every launch, every user, both launchers — the entire "two desktop icons, zero terminals" experience the product's own site pitches (site/index.html:167, "two desktop icons, zero terminals").

**Fix path:** Minimal fix: a single `[console]::Title` or a tiny always-on-top "starting HALO…" window/toast at launch start, updated at each named stage, closed on success/failure. Even a Windows balloon/toast notification at each of the 3-4 stage transitions would close most of this gap.

### 6 — The public landing page's Sessions-tab screenshot predates the STALLED/stop feature entirely — **Major**

**Category:** docs-accuracy / newcomer-trust

**Evidence:** `site/index.html:145` embeds `images/mission-control-sessions.png`, alt-texted "showing per-session context fill with amber warnings and token headroom." `site/images/mission-control-sessions.png` and the identical copy under `docs/images/` are both dated 2026-08-19 19:34, and `git log --follow` on that file shows exactly one commit: `3d05392 2026-08-19 "v0.4.0: annotated console screenshots..."`. The STALLED/stop feature is dated 2026-08-20 by the code's own comments (e.g. `mission-control.mjs:2648-2649`, `:1272`, `:429` all cite "2026-08-20" as the incident that motivated it) — one day *after* the screenshot. I opened the image directly to confirm rather than infer from dates alone: the rendered table has 10 columns ending at UPDATED, every row shows a green "idle" dot, and there is no trailing action column at all — no stop button, no STALLED row, matching a pre-feature 10-column layout against the current code's 11-column layout (`mission-control.mjs:1792`, header ends `...<th>Updated</th><th></th>`).

**Observed vs expected:** Expected: the screenshot illustrating the Sessions tab shows what the Sessions tab currently does. Observed: it shows a strictly older version, missing the exact feature this review — and the site's own copy — makes a point of.

**Why it matters:** The same page's "Honest status" section (site/index.html:201) explicitly boasts about this fix: *"Mission Control displayed that dead run as healthy the entire time. Those three defects are fixed and the fixes are proven on hardware."* A newcomer reading that claim and then looking at the very screenshot meant to back it up sees no evidence of it — no stalled row, no stop control, no action column. This is the same "documentation ahead of what's actually shown" pattern this whole audit is sensitized to, just running the other direction (the *code* moved past the *screenshot*, not past the claim).

**Impact scope:** The public marketing surface for this exact feature — every visitor to the landing page evaluating whether Mission Control does what the copy says.

**Fix path:** Retake `mission-control-sessions.png` (and check the other five for the same staleness while at it) against current master with a stalled row visible, and swap it into both `site/images/` and `docs/images/`.

### 7 — README's version banner is stale by four releases — **Minor**

**Category:** docs-accuracy

**Evidence:** `README.md:3` — **`Version v0.1.0` — first versioned release, 2026-08-18.** `CHANGELOG.md:6` — the latest entry is `## [0.5.0] - 2026-08-20`. `site/index.html:75` — the landing page's own hero pill correctly reads `v0.5.0`. The site's header nav (`site/index.html:9`) links "Changelog" straight to the GitHub CHANGELOG, and "Get the stack on GitHub" links to the repo root (the README) — a newcomer bouncing between the two pages the project itself links together will see `v0.5.0` and `v0.1.0` within one click of each other.

**Why it matters:** Not functionally blocking, but it's the very first line of the most-read file on a public repo, and it actively understates the project's maturity/fix history (four releases of real fixes, including a prompt-injection fix in 0.5.0, are invisible to a README-only reader) — the opposite direction of the overstatement pattern this audit is watching for, but the same underlying defect: the doc doesn't match reality.

**Fix path:** One-line edit to `README.md:3`.

### 8 — Simultaneous secondary alarms are color-only — **Minor**

**Category:** accessibility / color-signaling

**Evidence:** `renderStrip()` (mission-control.mjs:1329-1352) picks exactly one `cause` string to display as text — the single worst light, first-in-order on ties (lines 1334-1338: `if(lv==='r'&&worst!=='r'){worst='r';cause=...}` etc.). Every light still gets a colored dot (`.light.g/.a/.r`, line 973) with its own cause in a `title` attribute (line 1345), but `title` tooltips are mouse-hover-only and the light-item span isn't focusable (see finding 4), so they're not reachable by keyboard either.

**Why it matters:** When two lights are simultaneously non-green (plausible — e.g. this same report's Walkthrough found a stalled session and a mis-pointed scheduled task in the same run), only the worse one is ever explained in visible text; the second is color-plus-hover only.

**Fix path:** Either list every non-green cause in the trailing `.alarm` text (joined), or add a small text badge under each non-green dot.

### 9 — Failure-message copy is uneven in actionability — **Minor**

**Category:** copy / newcomer-UX

**Evidence:** Compare `Start-DSH.ps1:64,86-88` ("MISSING PREREQUISITE: 'lms' is not on PATH. Install LM Studio, then run its CLI bootstrap so 'lms' is on PATH (README step 1)") and `:107` ("open LM Studio once by hand and check its Developer/Server tab") — both name one precise, single next action — against `:201` ("Port is held but the page does not answer - wedged server (known rc.7 defect with sessions >1MB), or a different app owns 3080.") and the raw 40-line stdout/stderr dumps from `Dump-ServerOutput` (lines 173-180, 192, 202) — both developer-register, no synthesized "try this" step. (This is a copy/actionability observation only; the brain-load-failure message's *factual accuracy* is already Critical per Walkthrough W1 and isn't re-litigated here.)

**Why it matters:** A newcomer who gets the good messages can self-serve; a newcomer who gets the "wedged server" message or a raw log dump cannot, without already knowing what `rc.7`, `>1MB sessions`, or the dumped npm output mean.

**Fix path:** Give the harness-never-served path the same single-action treatment as the prerequisite checks — e.g. "close any other app using port 3080, or restart the machine and try again."

## What's working

- **The alarm strip's STALLED prioritization is correctly implemented and well-written.** `computeLights()` checks stalled sessions before every other HARNESS condition (mission-control.mjs:1271-1279), and the resulting text is genuinely actionable for a non-expert: it names the exact session, states the idle duration in plain units (`fmtDur` — "4h41m", not a raw millisecond count), and closes with a concrete instruction: *"stop them or investigate."* This is exactly the kind of copy the rest of the report asks for elsewhere.
- **STALLED is self-explanatory without relying on color.** The word "STALLED" plus a plain-English duration (line 1767) carries the meaning on its own — a real, deliberate choice, not an accident (see finding 1 for the one place this redundancy is missing: the dot itself).
- **The stop button's confirm copy clears a real bar.** `'Stop session: ' + title + ' - this cancels its current turn. Findings already written to disk are kept.'` (line 1215) does two things most confirm dialogs don't: names the specific consequence, and proactively reassures on data loss — well above a bare "Are you sure?"
- **The stop button and every tab button are real, semantic `<button>` elements** — natively focusable, natively operable by keyboard, and nothing in the file strips the default focus outline. The control named in scope for this review passes keyboard reachability cleanly.
- **The backend stop endpoint has clear, differentiated failure copy.** `mission-control.mjs:2652-2668` distinguishes "harness refused (HTTP {status})" from "could not reach the harness on :3080 — {message}" — a real, useful distinction surfaced to the operator, not swallowed.
- **Both launchers correctly refuse to open a browser at a dead port**, verified by the Walkthrough lane and confirmed again in source (`Start-DSH.ps1:190-204`, `Start-MissionControl.ps1:60-71`) — a newcomer never lands on a blank/error tab, which is a real, meaningful first-run safety net even though the surrounding feedback has gaps (findings 5, 9).
- **Destructive actions elsewhere in the console set a good precedent** the stop control could still learn from: `act()`'s unload-all/unload-worker path (lines 1225-1235) names the exact models and freed GB before confirming, and danger buttons are visually and structurally separated (`.danger-cluster`, line 1077) from safe ones.
- **The console explains a lot of genuinely tricky domain concepts inline, not just in docs** — fleet/LM Link consequences (`mission-control.mjs:1687`: "This model runs on another LM Link device. Unloading from here would kill it on THAT machine."), the GPU shared-pool leak signal (line 1654), the drive-root workspace bug (line 1091), and context-window risk (line 1734) all have real `title=` tooltips written for an operator, not a developer.
- **The landing page's "Honest status" section is a standout.** `site/index.html:201`: *"Until 2026-08-21 the loader scripts imported an SDK that was never committed to this repository, so the stack could not load a model on any machine but the author's — five releases shipped in that state... Mission Control displayed that dead run as healthy the entire time."* This is plain, specific, and admits real failure on a public page — rare, and directly the kind of trustworthy disclosure this whole audit is testing for.
- **Site screenshots carry genuinely descriptive alt text** (`site/index.html:141,145,149`), and color contrast for the dominant text color against the dark theme is comfortably high (spot-checked `--mut #9fb3c8` against the darkest background `#0c1420` ≈ 8.6:1, well past WCAG AA).
- **"How it works" (site/index.html:90-98) is well-written newcomer copy** — brain/worker/cockpit/glass are each introduced with a plain one-paragraph description before any jargon, a real, deliberate structure choice.

## What I could not assess

- I read the code and one rendered screenshot; I did not drive the live console in a browser this session (no running dsh/LM Studio session was available to me here), so I could not confirm rendering pixel-for-pixel beyond the one screenshot I opened, nor test actual screen-reader output — the accessibility findings are static-markup analysis (presence/absence of ARIA/tabindex/alt text), a reliable proxy but not a full assistive-technology pass.
- I did not verify whether clicking "stop" on a genuinely *stalled* (frozen, not just busy) session actually unsticks it at the harness level (`/api/session.cancel` on :3080) — that's a backend behavior question outside what static reading of the console can confirm.
- I did not check `mission-control-overview.png`, `-models.png`, `-plugins.png`, or `-system.png` for the same kind of staleness I found in `-sessions.png` — I spot-checked the one most relevant to this review's scope.
- I did not test actual Windows Notepad window-reuse behavior (finding n3) — inferred from `Start-Process notepad` semantics, not observed on this machine.
- I did not review `docs/USER-MANUAL.md` copy — the task scoped copy review to README.md, site/index.html, and the console specifically, and I kept to that.
- Contrast was spot-checked on one representative color pair by hand, not run through an automated checker across every color/background combination in both files.
