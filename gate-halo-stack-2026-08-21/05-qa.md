## Findings

### QA1 — Mission Control's live process is running stale code; the session-stop kill-switch is dead right now — **Critical**

**Evidence:**
- `netstat -ano` confirms PID **31072** owns the listening socket on 127.0.0.1:3090.
- `Get-CimInstance Win32_Process` shows PID 31072's `CreationDate = 8/21/2026 12:56:58 AM`, command line `node.exe "C:\Users\scott\.dsh\mission-control\mission-control.mjs"`.
- The file it was launched from has `mtime = 2026-08-21 02:03:10` — **66 minutes after the process started** — and is byte-identical (`diff` confirms) to the repo's `mission-control/mission-control.mjs`, which contains the handler at line 2652: `if (req.method === 'POST' && url.pathname === '/api/action/stop-session') {...}`.
- `~/.dsh/ConfigBackups` shows **four deploys today** (`deploy-20260821012638`, `-012704`, `-015727`, `-020848`), all of which post-date PID 31072's start — i.e., this process has survived every deploy run today without restarting.
- Live probe: 7 variants sent to `POST /api/action/stop-session` — no body, `{}`, string id, numeric id, object id, array id, malformed JSON — **all return `404 Not Found` / `unknown action`**, the generic ACTIONS-dictionary fallback (mission-control.mjs:2670-2674), not the specific handler. This is reproducible and did not change when dsh cockpit (:3080) came up mid-session.
- The "stop" button is real and wired: rendered only when `s.claimsRunning` (mission-control.mjs:1781) — i.e. exactly when an operator has a stuck session — calling `stopSession()` (line 1211), whose failure path shows `'could not stop: ' + t` (line 1220) in the UI, so the operator sees "could not stop: unknown action" at the exact moment they need this feature.
- Root cause located: `Start-MissionControl.ps1:22-34` — `Test-MCServing` + `if (Test-MCServing) { ...reusing it... exit 0 }` — is explicitly idempotent-by-design and never restarts an already-serving instance. `Deploy-ToLive.ps1` has **zero reference to port 3090 or Mission Control's process** anywhere in its pipeline (only a file-copy mapping at line 61).

**Why it matters:** this feature exists specifically because "the only remedy for a runaway was killing the whole dsh process" (mission-control.mjs:2649-2650, dated 2026-08-20). It is fully coded, fully deployed to disk, fully wired into the UI — and does not work, with no diagnostic anywhere pointing at "restart Mission Control." It is the second process (after Walkthrough's W2, the Scheduled Task) shown to silently drift from what "deploy succeeded" implies. Since Start-MissionControl.ps1's reuse-if-serving behavior is the *documented, intended* fast path, staleness is the **normal** outcome for a returning user, not an edge case.

**Impact scope:** every returning user who leaves Mission Control running across a deploy — which, given the reuse-by-design launcher, is the default case — silently loses the one safe way to end a stuck session, with the UI's own error message ("unknown action") actively misleading them about the cause.

**Fix path:** either (a) have Deploy-ToLive.ps1 unconditionally restart the MC process at the end of a successful deploy, or (b) add a build-fingerprint endpoint (e.g. hash mission-control.mjs at startup, expose via `/api/status`) and have Start-MissionControl.ps1 compare it against the on-disk file before taking the reuse fast path, restarting on mismatch and saying so.

**Test:** touch mission-control.mjs, run Start-MissionControl.ps1 against an already-running instance, assert the new route is live (or that the launcher visibly restarted).

### QA2 — Mission Control's action endpoints have no auth, no Origin check, and no CORS handling; five require zero body — **Critical**

**Evidence:**
- Source-wide grep for origin/referer/csrf/auth/token/bearer/apikey in mission-control.mjs: no access-control hits.
- Live: `OPTIONS /api/action/stop-session` with `Access-Control-Request-Method: POST` → `404 Not Found`, no `Access-Control-*` headers at all — the server does not answer CORS preflight.
- Live: identical `400 path and modelKey required` from `POST /api/action/load-model` whether sent with `Content-Type: application/json` or `Content-Type: text/plain`, and identical whether or not `Origin: http://attacker.example` is set — proving `readBody()` (mission-control.mjs:922-929, raw `JSON.parse(data)`) and the router are both Content-Type- and Origin-blind.
- Source: 5 of 9 actions in the `ACTIONS` dictionary (mission-control.mjs:914-920 — `start-cockpit`, `load-q5`, `load-worker`, `unload-worker`, `unload-all`) are dispatched at lines 2670-2674 **without ever calling `readBody()`** — a bare `POST` with no body at all is sufficient.

**Why it matters:** `Content-Type: text/plain` is a CORS-"simple" content type — a cross-origin `fetch` or an auto-submitting HTML `<form>` using it needs **no preflight**, so the browser sends it straight through, and this server does not check the `Origin` it arrives with. Any web content the operator's browser loads while Mission Control is running — a bad ad, a compromised page, an XSS'd site — can blind-POST to `/api/action/unload-all` (evicts every resident model) or `/api/action/start-cockpit` (spawns a hidden `powershell.exe -WindowStyle Hidden` running Start-DSH.ps1, which loads a 21 GB model and opens a browser tab) with zero body and zero sophistication. This is the well-established "unauthenticated localhost companion server" CSRF class, not a theoretical chain — every non-destructive precondition here was independently verified live.

**Impact scope:** any user who runs Mission Control (its steady-state default) and browses the web in the same session — effectively the whole target audience of a local-AI coding workstation.

**Fix path:** require a per-install shared-secret token (e.g. generated to `~/.dsh/mission-control/token` at first launch, sent as a header, checked on every `/api/action/*` POST) and/or reject requests whose `Origin`/`Sec-Fetch-Site` isn't same-origin; answer `OPTIONS` explicitly rather than falling through to a 404.

**Methodology note:** I did not fire the real destructive actions to complete an end-to-end exploit — this conclusion combines verified server-side preconditions (no Origin check, no preflight handling, Content-Type-blind parsing, bodyless dispatch) with standard, documented Fetch/CORS platform behavior, not a live cross-origin browser demonstration this session. See "What I could not assess."

### QA4 — No concurrency guard anywhere in Deploy-ToLive.ps1 — **Major**

**Evidence:** exhaustive grep of the full 32 KB script for mutex/lock/semaphore/"already running"/PID-file patterns: zero matches. By contrast, `Start-DSH.ps1:70` takes `New-Object System.Threading.Mutex($false,'Local\HaloStackLauncher')` specifically because "two launchers racing... could force-kill each other's still-starting server and clobber each other's logs" (its own changelog, item 9) — the team has already fixed this exact bug class for the launcher but not for deploy. `$stagingHome`/`$backupRoot` (Deploy-ToLive.ps1:352, 368) are both named with second-granularity timestamps only, so two runs in the same second collide on their own paths outright; runs seconds apart still apply to the same live destination files with independently-run, uncoordinated backup→apply→validate cycles (last write wins; whichever run's validate step runs last determines the reported PASS/FAIL, potentially validating the *other* run's output).

**Why it matters:** deploy has run 4 times in ~42 minutes today (01:26:38→02:08:48 per ConfigBackups) — overlap from an impatient re-run, two terminals, or a scheduled deploy firing mid-manual-run is a plausible real trigger, not contrived. Walkthrough's W2 already demonstrated one out-of-band casualty (the Scheduled Task) from *non-concurrent* deploys; an actual race multiplies that risk across every file the deploy touches, with no error surfaced to the operator.

**Impact scope:** any workflow where deploy could plausibly run twice close together — silently corrupts live config/backups with the tool still reporting success.

**Fix path:** acquire a named mutex or PID lock file at the top of Deploy-ToLive.ps1, matching the pattern already proven in Start-DSH.ps1.

**Methodology note:** assessed via static code reading only — I did not launch two concurrent deploys against this operator's live machine (resident 21 GB model, 2 connected fleet peers), since that is exactly the kind of repository/live-state modification the read-only mandate excludes.

### QA5 — ConfigBackups and per-run logs grow strictly unbounded, no retention anywhere — **Major**

**Evidence:** `~/.dsh/ConfigBackups` holds **25** `deploy-*` directories spanning 2026-08-18 09:50 through 2026-08-21 02:08 (3 days), 5.7 MB total — the oldest (Aug 18 09:50) is still present, nothing has ever been removed. `~/.dsh/logs` holds 3 timestamped `dsh-server-*.{log,err.log}` pairs, all from today (mtimes start 01:28 — this per-run capture scheme is new as of today, per Start-DSH.ps1's own changelog item 5). Repo-wide grep for retention/prune/cleanup/MaxAge in Deploy-ToLive.ps1 and Start-DSH.ps1: no real hits.

**Why it matters:** the task brief itself named this exact risk, and it's confirmed. Today's absolute numbers are small (~230 KB/backup, ~40 bytes/log-pair because nothing has hard-failed yet), but there is no ceiling on either directory, and this is a workstation meant for months of daily use with no operator-visible warning as they grow. A real crash loop would write much larger `.err.log` files under the same zero-retention policy.

**Impact scope:** every long-lived install, worsening with usage frequency.

**Fix path:** cap both directories by count or age (e.g. keep last N or last 14 days) at the start of each deploy/launch.

**Positive counter-evidence (idempotency, not accumulation):** `diff`'d `Start-DSH.ps1` between today's last two backups (`deploy-20260821015727` vs `-020848`) came back **byte-identical**; `settings.yaml` between the same two showed a real, deliberately-commented config change (`retryPolicy`/`compactionRetries`, referencing a genuine 2026-08-20 incident). The deploy mirrors real source changes faithfully and does not inject noise on unchanged files — the defect is purely that the resulting backup/log directories are never pruned, not that content is corrupted or non-deterministic.

### QA3 — `ACTIONS` dictionary lookup walks the prototype chain: one 500, two spurious 200s — **Minor**

**Evidence (live, harmless — all three are inert `Object.prototype` members, nothing dangerous is reachable):**
```
POST /api/action/__proto__        → 500 "TypeError: ACTIONS[a] is not a function"
POST /api/action/toString         → 200 "ok"   (does nothing)
POST /api/action/hasOwnProperty   → 200 "ok"   (does nothing)
```
`ACTIONS` is a bare object literal (mission-control.mjs:914) indexed directly by `url.pathname.split('/').pop()` (line 2671) guarded only by `if (ACTIONS[a])` — which resolves inherited `Object.prototype` members as truthy/callable. This is the only input across ~30 probes this session that produced a 500 or a wrong-but-200 response; every genuine malformed input elsewhere (bad JSON, wrong types, missing fields, path traversal, wrong HTTP verbs, out-of-range query params) degraded cleanly to a sane 4xx.

**Fix path:** `Object.hasOwn(ACTIONS, a)` guard, or build `ACTIONS` with `Object.create(null)`.

Live-observed: `sessionsSource` correctly flipped from `"disk scan (dsh down)"` to `"dsh api"` the moment :3080 came up mid-session, confirming this is the live, in-use gate — just not upgraded to the identity-checked version deployed elsewhere in the same repo on the same day.

**Fix path:** reuse the `__DSH_BOOT__`-identity HTTP check already written for Start-DSH.ps1's readiness probe here too.

## What's working

- **Genuinely robust error handling.** Across ~30 malformed/edge-case requests (missing bodies, wrong types, unknown ids, invalid JSON, path-traversal attempts, wrong HTTP verbs, out-of-range/non-numeric query params), the API never returned a stack trace or crashed — every case but the deliberately-constructed `__proto__` edge case (QA3) produced a clean, human-readable 4xx. The top-level `try/catch` (mission-control.mjs:2516, 2676) and per-route validation both hold up in practice, not just on paper.
- **Query-param clamping verified live**, not just in source: `/api/history?hours=` correctly clamps negative values to 1, huge values to 336, and falls back to the default 6 on non-numeric input (`hours=banana`) — matches mission-control.mjs:2579 exactly.
- **No secrets leaked.** Direct grep of live responses from all 6 GET endpoints tested (status, sessions, plugins, catalog, memory-graph, logtail) for `LMSTUDIO_API_KEY`, `EXA_API_KEY`, and generic `sk-...`-style tokens: zero hits. `.env` is never read by mission-control.mjs at all (confirmed by source grep). Caveat: `/api/status` and `/api/sessions` do return local absolute paths (`workspace` field, e.g. `C:\Users\scott\Desktop\Code` — inconsistently normalized, some entries shortened to `Desktop-Code`) — low severity on a loopback-only, single-user tool, but worth knowing if this surface is ever bound wider than `127.0.0.1`.
- **No arbitrary-file-read surface.** Only three places in the whole file use a request-derived value (`hours` → numeric clamp, `raw` → boolean flag, action name → fixed-dictionary key); none construct a filesystem path from user input. `/api/logtail`'s path is hardcoded to a fixed LM Studio log directory scan.
- **Loopback-only bind** (`server.listen(PORT, '127.0.0.1', ...)`, line 2716) — materially limits QA2's blast radius to this machine's own browser rather than the LAN.
- **Real defensive fixes with real incident histories, credited:** the `unload-model` remote-fleet guard (mission-control.mjs:2637-2644, refuses with 403 rather than killing a model resident on another LM Link device — "the 5070 Ti port found this button could kill a remote box's active brain") and the client-side destructive-action confirms that name exactly what they're about to destroy before asking ("One misclick used to evict every resident model with no confirm and no undo") are both genuine, targeted fixes for real prior incidents, not cosmetic.
- **Start-DSH.ps1's launcher mutex** (`Local\HaloStackLauncher`, line 70) is a real, correctly-scoped concurrency guard — it's just not extended to Deploy-ToLive.ps1 (QA4).
- **Deploy is content-idempotent, not just backup-accumulating.** Directly diffed: `Start-DSH.ps1` byte-identical across today's last two deploys; `settings.yaml` differed with a real, well-justified, well-commented change between the same two runs. The deploy faithfully mirrors true source changes and introduces no noise on repeats — the growth problem (QA5) is purely retention, not correctness.

## What I could not assess

- **QA2's exploit was not fired end-to-end.** I verified every server-side precondition live and non-destructively (no Origin check, no CORS preflight handling, Content-Type-blind body parsing, bodyless dispatch for 5 actions), but did not stand up a second browser origin and actually complete a cross-origin CSRF this session. The browser-side half rests on standard, documented Fetch/CORS behavior, not an independent live demonstration.
- **QA4's race was not reproduced**, only assessed from static code — running two real deploys concurrently against this operator's actively-used machine (resident 21 GB model, 2 connected fleet peers) would itself violate the read-only/no-modification mandate.
- **stop-session's true forwarding behavior is unverified.** Because the live process never reaches the specific handler at all (QA1), I could not observe what a legitimate nonexistent-sessionId request would actually get back from the `:3080` `session.cancel` proxy path (400? 502? something else?) — the exact scenario the task asked about is blocked pending a Mission Control restart, which I did not perform myself, and I did not route around it by hitting `:3080/api/session.cancel` directly since that endpoint wasn't the one named and probing the harness's raw internals felt like scope creep for uncertain benefit.
- **`POST /api/validate-config` was read from source only, not invoked** — it shells out to `npx @deepseek-ai/dsh@<pin> web --dump-config` with a 120s timeout; likely read-only in effect but costly to run for uncertain incremental value, so skipped.
- **Long-run disk-growth extrapolation for QA5 is not measured** — I have today's rate (4 backups + 3 log-pairs in a few hours) but not a multi-week projection, and I don't know how large `.err.log` gets during a genuine crash loop versus today's ~44-byte quiet samples.
- **No load/stress testing** of Mission Control under many concurrent requests — out of scope for this pass.
- **dsh cockpit (:3080) state changed mid-session** (down at start, up by ~08:11:14 UTC — essentially simultaneous with my first probe, almost certainly the operator or another concurrent process, not an action I took) — this let me observe both the down-state (`sessionsSource: "disk scan (dsh down)"`) and up-state (`"dsh api"`) for `/api/sessions`, but I only captured `/api/plugins`'s down-state short-circuit from source, not by direct live observation in that exact state.
